# ADR 0005: configurable MFA and optional passkeys

Status: Accepted

Administrators configure Optional, Administrators (default), or Everyone MFA enforcement. Saving administrative settings requires the settings permission but no additional password or factor confirmation. Users own their authenticator and passkey enrollment. The default bootstrap administrator receives a setup-only session, which permits profile and enrollment operations but no user directory or administrative work. Policy is read from PostgreSQL on session validation, so tightening it takes effect across replicas and existing sessions immediately.

Password verification produces a ten-minute, single-use challenge instead of a session whenever the account has a configured MFA method. The challenge returns only the methods configured for that account and selects the user's stored preference; verified email is the default preference when no valid preference exists. The user can switch between configured email, authenticator and passkey methods without repeating the password step. Successful verification returns the user to the originally requested same-origin route. A normal rotating session remembers the completed MFA verification for its existing 30-day lifetime; there is no separate trusted-device bypass.

Confirming an email automatically enables email-code MFA. Bootstrap administrators retain their non-deliverable reserved address only for Identity compatibility, so email MFA is not enabled for that address and policy enforcement gives them a setup-only session until they enroll an authenticator or passkey. Email codes contain six random digits, expire after ten minutes, and are encrypted both in challenge state and in the durable email outbox. Resending rotates the code and is limited to once every 30 seconds per account. Five invalid email-code attempts impose a ten-minute email-method cooldown shared across replicas; another configured method remains usable. The code and message payload are never logged.

Authenticator verification accepts TOTP or a one-use recovery code; recovery-code entry is exposed only within the authenticator method. Passkey MFA uses a user-scoped WebAuthn assertion tied to the original password challenge. Passkey sign-in remains an optional, independently verified path. TOTP and recovery-code verification are serialized per user and enforce Identity lockout. Accepted TOTP counters are persisted to reject replay. Recovery codes are shown only when generated. Changing factors changes the security stamp, revokes other sessions, records an audit event and queues a notification. Factor management requires password reauthentication and the existing authenticator when enabled. Email- or passkey-only accounts require a recently verified session for factor management.

Optional passkeys use .NET 10 IPasskeyHandler with required user verification and an RP ID derived from Web:PublicUrl. A verified passkey can satisfy MFA without an additional TOTP prompt. Passkey challenge state is encrypted with Data Protection and stored in PostgreSQL; no credential material or challenge state is logged. Registration does not transfer existing credentials between users. Assertion counters are updated under serialization. Passkeys are not portable to a different RP domain: decide the production domain before enrollment.

No MFA bypass is granted to administrators. Users should keep a second passkey/device or authenticator recovery codes. Password reset does not disable MFA. If every factor is lost, use a separately governed operator recovery procedure with identity verification; this release does not expose an administrative bypass endpoint.

Browser refresh, password login, passkey login and logout use one Web Lock. Cross-tab logout clears local state. CSRF tokens deliberately use the anonymous principal both when issued and verified: the double-submit cookie/token remains required, alongside exact Origin validation, but token validity is independent of expiring JWT identities. Authorization still uses the original authenticated principal.

Validation: PostgreSQL challenge, email cooldown, recovery and permission tests; Playwright virtual-authenticator enrollment and login; generated OpenAPI contracts. Hardware, OS account recovery and platform-specific passkey syncing remain deployment acceptance checks.
