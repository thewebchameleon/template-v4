# ADR 0024: structured audit event details

Status: Accepted

Audit History uses the shared data table's row action to open an accessible right drawer. The list remains paginated and sortable; `GET /api/v1/auth/audit/{id}` loads details separately. Both endpoints require `settings.manage` and the `audit-history` module. Detail loading, failure/retry, keyboard activation, close, and focus restoration use the shared page-state, table and Spartan drawer conventions. English and Afrikaans copy is maintained together.

Audit events remain explicitly authored by the service that owns the operation. `AuditCapture`, a scoped EF SaveChanges interceptor, enriches new entries with schema version, actor and subject name snapshots, actor/subject types, outcome, source and trace context. It does not discover changes by serializing tracked entities. Infrastructure services supply allowlisted `AuditChange` values, optional related entities and string metadata. `AuditCapture.Changes` omits unchanged values. All runtime writers use asynchronous SaveChanges; do not use synchronous SaveChanges for audited operations.

Action codes are stable (`role.granted`, `user.role_granted`, `security.policy_changed`); permission, role and policy values live in structured changes. Existing action strings remain readable. New name snapshots are authoritative, including a null snapshot after redaction; only legacy entries resolve current user/role names. API source means an HTTP request and does not claim to distinguish a browser from another client. Background and bootstrap sources are explicit. Existing failed-login and refresh-reuse events record failure/denial; an unauthenticated failed login does not attribute the attempted action to the account owner. This change does not add auditing to every rejected request.

The nullable, additive migration leaves old events unversioned. The drawer labels missing historical context as not captured and explains that legacy names are current lookups. JSONB holds only typed changes, related identities and allowlisted metadata; list queries do not retrieve these payloads. A change's null before/after value means not set, not a reconstructed historical value.

State changes and their audit entries retain their existing transaction boundaries. Audit success means the recorded domain operation succeeded; audit rows roll back with failed transactions. Expected failures that already commit an audit event retain that separate behavior. Audit events are not general diagnostic logs: never capture passwords, tokens, authorization headers, email action URLs, message bodies, or arbitrary request/entity dumps. Request IP and user-agent capture are not enabled. Reason is optional and reserved for explicit administrative justification; no free-text reason collection is added here.

Historical names are personal data. The existing account anonymisation transaction clears actor snapshots and subject/file snapshots, changes, metadata, reasons and related details for the erased account and its owned files. Related user records currently store identifiers without name copies. Any new personally identifying metadata or related-name capture must extend that redaction path and its integration coverage.

To extend auditing, add a stable action and localized label, explicitly supply the subject type for new record kinds, capture only the relevant safe before/after fields, and add real PostgreSQL behavior coverage. Register new detail queries explicitly, preserve permission/module gates and regenerate OpenAPI/clients through their owning tools. Do not backfill historical values from current state.
