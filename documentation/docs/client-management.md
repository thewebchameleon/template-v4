# Client management and licensing

The central application is the template plus the private `client-management` module
in [brinksolutions/business-modules](https://github.com/brinksolutions/business-modules).
It provides a provider-only client/deployment dashboard, enrollment, shared or
client-restricted paid offers, payment-derived licences, a release feed and deployment
preflight. See [ADR 0046](adr/0046-commercial-client-management.md).

## Central setup

Use a separate central deployment and database. In its private client selection,
include `client-management`; do not add the management module to customer builds.
Follow [business module composition](business-modules.md) to build all hosts, retain
reviewed locks, run the Migrator and deploy. Client management has its own permanent
migration history and requires the foundation's DeploymentLicenseSnapshots migration.
Existing client selections are not changed by this implementation.

Generate signing settings and a separate publication credential using new private paths:

```sh
node tools/deployment-client.mjs init-central /private/central.json /private/publisher-token
```

Supply `ClientManagement:SigningKey`, `ClientManagement:PublisherTokenHash` and
`ClientManagement:PublisherModules` from that configuration through the existing
secret/configuration mechanism. Add the actual allowed module IDs to PublisherModules;
the initial list contains only foundation. Never commit these files or put keys/tokens
in command arguments, URLs, images, build arguments or logs. Files are created with
owner-only permissions on Linux; restrict their ACLs explicitly on Windows.

Administrators with `settings.manage` can open **Client management**. Create a client,
register its environment and HTTPS application URL, and copy its one-time enrollment
token. Tokens expire after one hour. Reusing a token is rejected. The provider sees all
registered clients and deployments; disconnected deployments retain their last-known
state. Recent contact is not a guarantee of application health. Application contact
becomes stale after 15 minutes; licensing freshness is evaluated independently.

Create an offer using the module's stable ID, immutable commercial terms, currency,
price, one-time/monthly/annual interval, use/update duration and `disable` or
`keep-installed` expiry policy. No selected clients means a shared offer; selected
clients restrict eligibility. Purchasing starts Stripe or PayFast checkout. Only a
verified callback or reconciliation result creates a receipt, subscription and
`license_entitlements` row. The previous manual entitlement route and table are removed;
existing manual grants are deliberately not carried forward.

Recurring purchases can be cancelled from Client management. Paid use/update deadlines
are derived from the settled offer and payment period. One-time licences follow the
offer duration/policy and cannot be cancelled as subscriptions. Configure credentials
under the foundation Payment methods settings; the private module stores its own orders,
receipts, subscriptions and licences and uses
`/api/v1/client-management/payment-callbacks/{provider}` for notifications.

The API supports revoking a deployment credential. Revocation stops new central
requests immediately; an already-issued client snapshot expires within its remaining
24-hour window. Automated credential/key rotation and in-place re-enrollment are not
implemented; do not rotate the central signing key without coordinating client public
keys and recovery. Retain installed release artifacts and recovery information.

## Client enrollment and enforcement

Mark each paid module descriptor with `"licenseRequired": true` before its release.
Host generation embeds the requirement. This does not change existing private modules
into paid modules automatically. Regenerate composition after descriptor changes.

Set `DEPLOYMENT_ENROLLMENT_TOKEN` through a private environment or secret manager, then:

```sh
node tools/deployment-client.mjs enroll /private/client.json https://central.example
```

This produces the client configuration and `/private/client.json.runner.json` with a
distinct runner credential. Supply only the client settings to API/Worker and only
the runner settings to the deployment process. Enrollment exchanges secrets over HTTPS;
the tool never prints them. The configuration file is not loaded automatically: merge
its Licensing and Updates sections through your platform's private app configuration
or equivalent environment variables. Keep the pinned installed metadata generated by
the release tooling. Required licensing settings must be present before starting a
host containing a paid descriptor. Unlicensed public foundation builds need none.

Worker refreshes signed licenses every five minutes. API capability gates read the
persisted snapshot and enforce identity, expiry and module dependency restrictions.
Expired access leaves data and migration history intact. Retention and privacy erasure
still follow their established policies. Administrator renewal information remains in
Updates. Each paid module must keep its authorized export/recovery endpoints outside
ordinary-operation gates; this implementation cannot infer exports for arbitrary
private data models. Review those boundaries before marking a module paid.

## Publish and discover releases

Use the existing [release workflow](release-updates.md), with the central feed URL:

```text
https://central.example/api/v1/client-management
```

Publishing uses the separately generated publisher credential. Reads use the enrolled
application credential. Component versions are immutable, and clients only see the
foundation and modules for which they have eligible entitlements. Repository/package
access remains separately scoped in GitHub; central licenses do not change registry ACLs.
Update notifications include runtime-disabled installed modules. A blocked update
explains that rights must be renewed. No notification initiates deployment.

## Client-triggered redeployment

Build and publish a pinned client release first. The deployment branch contains
`release.json` with component metadata and image digests; keep the previous installed
release record outside the incoming release directory. Run from a trusted foundation
tool checkout on the Linux VPS:

```sh
node tools/deployment-client.mjs deploy /private/client.json.runner.json /srv/client-release /private/installed-release.json
```

An optional final ISO timestamp with an explicit time zone schedules this invocation.
It must remain running, for example under your service supervisor. The executor targets
the VPS's local `/var/run/docker.sock`; remote Docker contexts are not supported.
A restart does not
resume an in-memory schedule. Publication never schedules it automatically.

The tool verifies central entitlement, the expected baseline, the published component
combination and digest-pinned Compose services. All writers, including Website where
present, stop before migrations. `DEPLOYMENT_BACKUP_USER` defaults to `postgres` and
`DEPLOYMENT_DATABASE` to `templatev4`; provide a role with backup access through the
container's established local authentication configuration. Backup failure stops the
rollout. The archive directory is checked with `pg_restore --list` before migration;
this is not a substitute for a restore drill. Secure backups outside a release directory
before cleaning old releases, and separately back up object storage and encryption keys.

Success writes a local receipt and reports installed versions centrally. Retain the
successful release.json as the next installed baseline. Failure after workloads stop
retains its `templatev4-deployment-<hash>.lock` in the OS temporary directory and any
backup. The hash is SHA-256 of the lowercase deployment ID, so all release directories
on that VPS share one lock. Inspect schema and running containers before
removing the lock or retrying. Never roll back by deleting migrations or automatically
restoring a database. Module removal currently fails preflight because retained-data
recovery must be explicitly designed for that module. Initial foundation installation
continues to use the existing Compose setup; enroll/report its baseline before using
the coordinated redeployment command.

## Verification

The private module's Tests project contains database-free licensing policy checks.
Generate the module OpenAPI contract through `Tools/ContractExporter`, passing an
absolute output path, then run its `ng-openapi-gen.json` with the foundation's generator.
Never edit generated contracts, clients or migrations by hand.

Browser checks and a full disposable-VPS deployment/recovery drill require explicit
permission under repository guidance and remain prerequisites for production rollout.
